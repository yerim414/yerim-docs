# 정보 구조 재설계

## 문제

사이드바에서 Python을 펼치면 하위 항목이 **54개** 나왔다. 그것도 평면으로.

스크롤을 한참 내려야 끝이 보이고, 원하는 문서를 찾으려면 눈으로 훑는 수밖에 없었다.
어떻게 꾸며도 정신없어 보이는 상태였다.

## 어디를 손봐야 하는지부터

"다 뜯어고치자"로 시작하지 않고, 먼저 **직속 하위 항목 수를 전부 세어봤다.**

| 메뉴 | 개수 |
| --- | --- |
| Python | 54 |
| 개발 지식 | 30 |
| Linux | 13 |
| SQL / MongoDB | 12 / 12 |
| Node.js | 11 |
| 나머지 7개 | 1~7 |

**문제는 두 곳뿐이었다.** 나머지는 12개 이하라 손댈 이유가 없었다.

전부 그룹으로 묶었다면 항목이 3~4개인 메뉴에까지 불필요한 계층이 생겼을 것이다.
숫자를 먼저 세어본 덕분에 작업 범위가 명확해졌다.

여기서 **"직속 하위 12개"를 기준으로 정했다.** 한 화면에 들어오고, 훑어서 찾을 수 있는 한계선이다.

## URL을 지킨 판단

그룹을 만드는 방법은 두 가지였다.

### 방법 A — 디렉토리를 실제로 나눈다

```
languages/python/문법-기초/unpacking.md
languages/python/객체지향/클래스.md
```

직관적이지만 **모든 문서의 URL이 바뀐다.** 이미 발행된 사이트라 기존 링크가 전부 깨지고,
리다이렉트를 50개 넘게 써야 한다.

### 방법 B — SUMMARY에서만 중첩한다

GitBook의 `SUMMARY.md` 중첩은 **파일 시스템 구조와 무관하게 동작한다.**
파일이 어디 있든 목차에서 원하는 대로 계층을 만들 수 있다.

```markdown
* [Python](languages/python/README.md)
  * [문법 기초](languages/python/groups/문법-기초.md)
    * [Unpacking](languages/python/unpacking.md)   ← 파일은 제자리
```

그룹 인덱스 페이지만 `groups/` 아래에 새로 만들고, 기존 문서 55개는 **한 개도 옮기지 않았다.**

**방법 B를 택했다.** URL이 하나도 바뀌지 않으니 리다이렉트가 필요 없고,
되돌리고 싶으면 `SUMMARY.md`만 원복하면 된다.

## 그룹을 나눈 기준

한 그룹에 **4~9개**가 들어가도록 맞췄다. 너무 적으면 계층만 깊어지고,
너무 많으면 그룹을 나눈 의미가 없다.

분류는 "문법이냐 아니냐" 같은 형식적 기준이 아니라 **찾을 때 어디를 뒤질까**로 정했다.
`timeit`은 성능 측정 도구지만 그룹을 따로 만들 만큼 문서가 없어서
`타입 & 코드 품질`에 넣었다. 코드를 다듬는 도구라는 점에서 mypy, Black과 같은 서랍이다.

## 사라진 URL 처리

구조 변경으로는 URL이 안 바뀌었지만, **문서 병합으로 4개 경로가 사라졌다.**
이건 `.gitbook.yaml`의 리다이렉트로 처리했다.

```yaml
redirects:
  languages/python/딕셔너리-언패킹: languages/python/unpacking.md
  languages/python/가상화-activaet: languages/python/가상환경.md
  languages/python/requests-verify-변수: languages/python/request-라이브러리.md
  languages/python/requests-요청-시-redirection-방지: languages/python/request-라이브러리.md
```

키가 이전 URL 경로, 값이 새 파일 경로다.

## 검증

구조를 바꿀 때마다 세 가지를 확인했다.

1. `SUMMARY.md`의 모든 링크가 실제 파일과 일치하는가
2. 목차에 등록되지 않은 문서가 있는가
3. 그룹 페이지와 섹션 README의 상대 링크가 유효한가

수동으로 확인하기엔 항목이 180개가 넘어서 전부 스크립트로 돌렸다.
