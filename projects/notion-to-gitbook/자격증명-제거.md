# 자격증명 제거

## 발견

저장소를 점검하다가 초기 커밋에서 평문 비밀번호를 발견했다.

| 종류 | 위치 |
| --- | --- |
| MSSQL SA 비밀번호 | `languages/python/mssql-연동.md` |
| MSSQL SA 비밀번호 | `projects/fastapi-pydantic/db-연결.md` |
| SSH 장비 비밀번호 | `languages/python/paramiko-invoke-shell.md` |

SSH 쪽은 접속 대상 IP와 계정명이 같은 줄에 함께 있었다.
**호스트·계정·비밀번호 3종이 한 세트로** 노출된 셈이라 비밀번호만 있는 것보다 위험했다.

Notion에서 글을 쓸 때는 비공개 공간이라 실제 값을 그대로 적었는데,
공개 저장소로 옮기면서 그대로 따라온 것이다.

## 1차 조치와 그 한계

문서 본문의 값은 플레이스홀더로 치환했다. 반복 작업이라 스크립트를 썼다.

```python
CREDENTIALS = [
    (re.compile(r"..."), "YOUR_PASSWORD", "MSSQL SA 비밀번호"),
    (re.compile(r"..."), "YOUR_PASSWORD", "SSH 장비 비밀번호"),
]
```

사설 IP(`192.168.x`)는 건드리지 않았다. RFC1918 대역은 민감정보가 아니고,
docker-compose 서브넷 설정처럼 **짝이 맞아야 하는 값이 깨지기 때문**이다.

문제는 여기서 끝난 게 아니었다. **워킹트리만 깨끗해졌을 뿐 커밋은 그대로 남아 있었다.**

```
8e90ae1  Remove credentials     ← 값을 지운 커밋
b64a280  Migrate from Notion    ← 값이 들어 있는 커밋
```

`b64a280`은 이미 푸시된 상태였다. 저장소가 공개라면 누구나 `git log -p`로 볼 수 있다.

## 우선순위 판단

두 가지를 해야 했다.

1. **노출된 비밀번호를 실제로 변경하기**
2. **히스토리에서 값 제거하기**

순서는 1번이 먼저다. **히스토리를 지워도 이미 노출된 값이 안전해지지는 않는다.**
누가 언제 복사해 갔는지 알 수 없기 때문이다.

이 경우엔 더 이상 쓰지 않는 값이라 1번은 건너뛰고 2번만 진행했다.

## 히스토리 재작성

커밋이 두 개뿐이고 자격증명은 `b64a280` 하나에만 있었다.
그래서 `git filter-repo` 같은 도구 없이, **두 커밋을 자격증명 없는 단일 루트 커밋으로 합치는** 방법을 썼다.

```bash
git checkout --orphan clean-root master   # master 트리로 부모 없는 브랜치 생성
git rm -q Sanitize.py                     # 치환 스크립트도 함께 제거
git commit -m "Migrate from Notion"       # 단일 루트 커밋
git branch -M master
```

작업 전에 백업 브랜치를 만들어 두었다. 되돌릴 수 없는 작업이므로 안전망이 필요했다.

## 놓칠 뻔한 것

재작성을 마치고 검증했더니 **새로 만든 "깨끗한" 커밋에서 비밀번호가 그대로 검출됐다.**

원인은 치환 스크립트였다. 스크립트의 `CREDENTIALS` 목록에 **비밀번호 원문이 하드코딩**되어 있었고,
이 파일이 워킹트리에 남아 있었으니 새 루트 커밋의 트리에도 포함된 것이다.

옛 커밋은 지웠는데 새 커밋이 같은 값을 다시 담고 있었다. 재작성의 의미가 없어질 뻔했다.

이미 역할을 다한 일회성 스크립트라 삭제하고 루트 커밋을 다시 만들었다.

**교훈은 명확하다. 히스토리를 재작성했으면 "지웠다"고 믿지 말고 반드시 전수 검사를 해야 한다.**

```bash
# 도달 가능한 모든 커밋에서 검색
for c in $(git rev-list --all); do
  git grep -qiE "패턴" "$c" && echo "HIT: $c"
done
```

## 브랜치 정리

master를 정리해도 **다른 브랜치가 옛 커밋을 참조하고 있으면 소용이 없다.**

당시 작업 브랜치 하나가 옛 히스토리 위에 올라가 있었다.
이 브랜치를 남겨두면 `b64a280`이 여전히 GitHub에서 접근 가능하다.
내용은 다른 브랜치에 포함되어 있었으므로 원격에서 삭제했다.

```bash
git for-each-ref --contains <옛커밋> --format='%(refname)'
```

이 명령으로 어떤 참조가 옛 커밋을 붙잡고 있는지 확인할 수 있다.

## 남은 위험

**force push를 해도 GitHub에서 옛 커밋이 즉시 사라지지 않는다.**

브랜치에서 참조가 끊겨도 SHA를 직접 알면 `github.com/<owner>/<repo>/commit/<sha>` 형태로
조회된다. 가비지 컬렉션이 돌 때까지 남아 있으며, 완전히 지우려면 GitHub Support에 요청해야 한다.

이번엔 더 이상 쓰지 않는 값이라 실질적 위험이 낮다고 판단하고 여기서 멈췄다.
다만 **"force push했으니 완전히 사라졌다"고 생각하면 안 된다**는 점은 기록해 둔다.

## 재발 방지

`CLAUDE.md`에 규칙으로 남겼다.

* 문서에 자격증명을 쓰지 않는다
* 예시가 필요하면 `YOUR_PASSWORD` 같은 플레이스홀더를 쓴다
* 사설 IP는 민감정보가 아니므로 그대로 두어도 된다
